## The problem

Clients struggle to find agents who fit their goals and locations. Agents need qualified leads in their service areas. Brokerages need to recruit agents who align with brand and territory. Most tools don't treat those three sides as one product.
The pitch was a network for all three types to do business.

## Role

I joined as a recent graduate and became the primary engineer: React SPA, ASP.NET Core API, matching UX, geospatial product work, and Azure CI/CD through production. Product leadership sat with Milad Akrami; other collaborators contributed on the frontend. Day-to-day delivery, deploys, and production issues sat largely on me.

## Architecture

Monorepo with a React SPA on Azure Static Web Apps, an ASP.NET Core 8 API on App Service, PostgreSQL with PostGIS and pgvector, Mapbox for maps, a FastAPI embedding sidecar, and an Azure Functions image pipeline. <strong>Environments: Dev, QA, and Prod.</strong>

## Matching (public version)

Matching is a hybrid pipeline: geospatial filtering, structured preference scoring by role, semantic similarity via embeddings in pgvector, then ranking with list caching and invalidation after profile changes. Exact weights and formulas stay proprietary.

> I combined structured scorers in C#, vector embeddings (MiniLM via a FastAPI sidecar), and PostGIS-aware geo filters, then cached ranked lists with invalidation, because matching was expensive enough that rate limits and cache policy were required.

## Hard parts

- **Multi-role surface:** One codebase for clients, agents, and brokerages. Shared primitives (auth, maps, cards) had to stay consistent while each path felt purpose-built.
- **Maps as a first-class dimension:** Agents draw service zones; clients mark preferred areas. Location drives matching, not just display.
- **API evolution:** Migrated toward a cleaner v3 surface while keeping v2 write paths alive so production never broke mid-migration.
- **Production ownership:** Dev to QA to Prod promotion, DNS for bridgesphere.ca, cookie-based auth, rate limits, CORS, and cold-start issues on the API tier.

## Tradeoffs

| Decision | Tradeoff | Why |
|----------|----------|-----|
| Hybrid matching + cache | Latency vs freshness | Full recompute was too slow |
| v2/v3 dual APIs | Complexity vs continuity | Could not big-bang migrate in production |
| Embeddings sidecar | Extra ops vs capability | Kept the .NET API focused |
| Hide score breakdown | Transparency vs IP | Protect methodology while keeping curated lists |

## Results

Shipped a live multi-role product on Azure with match lists, map-driven zones, auth and onboarding, saved profiles, analytics, and an image pipeline. CI/CD promotes through Dev, QA, and Prod.

Honest gaps: messaging and scheduling did not ship; UI libraries need consolidation; matching latency is still a product constraint.

## Reflection

The biggest lesson was that production is a feature. Matching and Mapbox demos matter, but so do branch promotion, secrets, DNS, and knowing what not to expose in the UI. I went from limited professional experience to owning a full-stack, multi-environment system end to end.
